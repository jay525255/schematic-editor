# 第一部分 · 这些文件分别是什么

## 1.1 三个"工程文件"的区别（最容易搞混的地方）

| 文件 | 大小 | 是什么 | 谁读它 |
|------|------|--------|--------|
| `SchematicEditor.sln` | 1 KB | **解决方案**（Solution）。它只是个"容器/清单"，记录这个解决方案里包含哪些项目、用什么配置编译 | Visual Studio 打开的就是它 |
| `SchematicEditor.vcxproj` | 8 KB | **项目文件**。真正的编译配置都在这里：源文件清单、包含路径、预处理宏、链接哪些库、输出到哪 | **MSBuild**（命令行编译时读的是它） |
| `SchematicEditor.vcxproj.filters` | 3 KB | 只控制 **Visual Studio 解决方案资源管理器里的分组显示**（"源文件""头文件""资源文件"那几个折叠夹） | 只有 VS 的界面读它，**不参与编译** |

**类比**：
- `.sln` ≈ 一本书的目录（可以装好几个项目，本项目只有 1 个）
- `.vcxproj` ≈ 某一章的正文内容（编译真正需要的东西）
- `.filters` ≈ 书签/分类标签（纯显示用，删掉也能编译）

**为什么命令行编译要指定 `.sln`？** 因为要给 MSBuild 一个入口，它会顺着 `.sln` 找到 `.vcxproj`。

```powershell
MSBuild SchematicEditor.sln /p:Configuration=Release /p:Platform=x64
```

## 1.4 从 `.cpp` 到 `.exe`：编译过程

```
 11 个 .cpp ──────→ cl.exe 编译 ──→ 若干个 .obj ─┐
                                                  │
 SchematicEditor.rc ─→ rc.exe ──→ .res ───────────┤
                                                  ├─→ link.exe ─→ SchematicEditor.exe
 wxWidgets 静态库（wxmsw32u_core.lib 等）──────────┘
 （在 D:\Test\wxWidgets-3.2.11\lib\vc_x64_lib）
```

- **编译**（compile）：每个 `.cpp` 独立翻译成机器码目标文件 `.obj`
- **链接**（link）：把所有 `.obj` + 用到的库拼成一个 exe
- **为什么 exe 有 6 MB**：wxWidgets 用的是**静态库**，用到的 wx 代码被直接复制进 exe，所以不依赖任何 wx DLL，拷到哪都能跑

# 第二部分 · 这个软件的原理

## 2.0 一句话概括

> 它是一个**图形化的图编辑器**：
> **数据**是一张图（元件是节点、导线是边）+ 从这张图算出的"网络"；
> **视图**把世界坐标乘上缩放、加上偏移，画成线；
> **交互**把鼠标事件翻译成对图的操作；
> **算法**用并查集从图求出电气连通关系，导出网表；
> **持久化**把内存对象写成 XML。

## 2.1 三层架构（最重要的设计原理）

```
┌─────────────────────────────────────────────┐
│  UI 层（wxWidgets 控件）                      │
│    MainFrame / LibraryPanel / PropertyPanel  │  只管"显示"和"接收输入"
├─────────────────────────────────────────────┤
│  视图/渲染层                                  │
│    SchematicCanvas                           │  把模型画到屏幕；把点击翻译成模型操作
├─────────────────────────────────────────────┤
│  领域模型层（纯数据 + 纯算法，不含界面）        │
│    NetModel                                  │  元件/引脚/导线/网络 + 连通性求解
├─────────────────────────────────────────────┤
│  IO 层                                       │
│    SchematicIO                               │  内存对象 ↔ 磁盘文件
└─────────────────────────────────────────────┘
```

**为什么这样分**：
- `NetModel` 完全不知道界面的存在 —— 它只接收 `vector<ComponentInstance>` 和 `vector<Wire>`，返回 `NetGraph`
- `SchematicCanvas` 只负责画和收事件，**一行电气语义都没有**
- 好处：答辩时如果老师问"换成 OpenGL 渲染要改多少？"——答案只需要改 `SchematicCanvas`，
  `NetModel`、`SchematicIO`、`MainFrame` 的接口完全不用动

## 2.2 程序怎么跑起来的：事件驱动 + 消息循环

**这是 GUI 程序和普通程序的根本区别。**

普通程序：`main() → 顺序执行 → 结束`
GUI 程序：`main() → 建窗口 → 进入消息循环 → 永远不返回`

```
wxIMPLEMENT_APP(SchematicApp)   ← 这个宏帮我们生成了 WinMain
        │
        ▼
  SchematicApp::OnInit()        ← 我们写的：建主窗口、显示
        │
        ▼
  wxApp::OnRun()                ← wx 提供的：进入消息循环（我们不用写）
        │
        └─ 无限循环：
             操作系统投递消息（鼠标动了、键按了、窗口要重画）
                  ↓
             wxWidgets 把消息翻译成 wxEvent
                  ↓
             派发给"目标窗口"
                  ↓
             我们在 Bind 里挂的处理函数被调用
```

所以代码里**没有"主流程"**，全是响应函数。`OnLeftDown`、`OnPaint` 这些不是被顺序执行的，
而是被"事件"触发的。

**事件的绑定方式**（`MainFrame.cpp` CreateMenus 末尾）：

```cpp
Bind(wxEVT_MENU, &MainFrame::OnCommand, this, wxID_LOWEST, ID_SIM_STOP);
Bind(wxEVT_TOOL, &MainFrame::OnCommand, this, wxID_LOWEST, ID_SIM_STOP);
```
意思是：ID 落在 `[wxID_LOWEST, ID_SIM_STOP]` 区间里的菜单/工具栏事件，统统交给 `OnCommand()`，
里面再用一个 `switch` 分发。**没实现的落到 `default` 分支显示"尚未实现"**。

## 2.3 界面怎么"拼"出来的：控件树 + Sizer + Splitter

wxWidgets 的界面是一棵树：

```
MainFrame（顶层窗口）
 ├─ wxMenuBar ──→ 8 个 wxMenu ──→ 76 条 wxMenuItem
 ├─ wxToolBar ──→ 17 个工具 + 分隔条
 ├─ wxStatusBar ──→ 5 个字段
 └─ wxBoxSizer（垂直布局器）
     └─ wxSplitterWindow（外层：左右分）
         ├─ LibraryPanel（左，固定 260 px）
         └─ wxSplitterWindow（内层：左右分）
             ├─ SchematicCanvas（中，占满剩余）
             └─ PropertyPanel（右，固定 300 px）
```

**两个关键机制**：

1. **Sizer（布局器）**：不用绝对坐标，而是声明"谁占多少比例、边距多少"。
   窗口大小变化时 sizer 自动重新分配 → 这就是为什么放大窗口时四个区会跟着变。
   代码里就是 `sizer->Add(控件, 比例, 标志, 边距)`。

2. **SplitterWindow**：一种特殊的父窗口，并排放两个孩子，中间有一条可拖动的 sash。
   ```
   m_splitOuter->SetSashGravity(0.0)   // 窗口变宽时，保持“左侧”宽度不变
   m_splitRight->SetSashGravity(1.0)   // 窗口变宽时，保持“右侧”宽度不变
   ```
   两个嵌套 → 得到"左固定 / 中伸缩 / 右固定"的三栏效果。

## 2.4 画布怎么"画"出来的：重绘机制 + 双缓冲 + 矢量绘制

### (1) 重绘机制：你不主动画，你只声明"我脏了"

```
数据变了 → 调用 Refresh() → 系统标记该区域无效
                              ↓
                        系统发 WM_PAINT
                              ↓
                        OnPaint() 被调用
                              ↓
              你负责把【整个客户区】从头画一遍
```

这就是为什么 `OnPaint()` 里是**从背景到前景完整画一遍**（背景→网格→导线→元件→框选→幽灵→预览→十字），
而不是"只画变化的那一部分"。

### (2) 双缓冲：为什么用 `wxAutoBufferedPaintDC`

如果每画一笔就直接送到屏幕，用户会看到线条一条条"蹦"出来（闪烁）。
双缓冲的做法是：**先给你一块内存位图，你画完，最后一次性贴到屏幕上**。
一行代码的事：`wxAutoBufferedPaintDC dc(this);`

### (3) 矢量绘制：`wxGraphicsContext`

提供抗锯齿的线段/矩形/椭圆/文字，坐标是**浮点数**。
所有绘制动作都是"把世界坐标转成屏幕坐标，然后描线"。

## 2.5 坐标系统原理（最核心的原理之一）

### 两套坐标系

| 坐标系 | 含义 | 谁在用 |
|--------|------|--------|
| **世界坐标** | 图纸自己的坐标，与屏幕无关 | 元件位置、导线端点**存的是这个** |
| **屏幕坐标** | 客户区像素坐标 | 鼠标事件、绘制 |

### 变换只有两个公式

```
屏幕 = 原点偏移 + 世界 × 缩放
世界 = (屏幕 - 原点偏移) / 缩放
```

对应代码只有 6 行：
```cpp
wxPoint2DDouble ToScreen(const wxPoint2DDouble& world) {
    return wxPoint2DDouble(m_origin.m_x + world.m_x * m_zoom,
                           m_origin.m_y + world.m_y * m_zoom);
}
```

- `m_origin` = "世界原点 (0,0) 落在屏幕的哪个位置"
- `m_zoom` = 缩放倍数

### 为什么要两套？

因为**缩放和平移只改这两个数，完全不用碰任何元件数据**。
这就是计算机图形学里"视图变换"的思想：**数据是稳定的，视图是随便动的**。

### "滚轮以光标为中心缩放"的原理

目标：缩放前后，光标底下那一点的世界坐标保持不变（内容绕光标缩放）。

```
1. 记下光标处的世界坐标：W = ToWorld(光标屏幕坐标)
2. 改 m_zoom
3. 反解 m_origin，使 ToScreen(W) 仍然等于原来的光标屏幕坐标
   → m_origin = 光标 - W × 新zoom
```
代码就是 `SetZoomAt()` 那 10 行。

## 2.6 交互原理：命中测试 + 工具状态机

### 每次左键按下，程序要回答一个问题："用户点到了什么？"

```
1. 屏幕坐标 → 世界坐标
2. 命中测试（从上层往下、从后往前找）
   ├─ 点在某个元件的矩形内（矩形外扩一个引脚长度）？ → 选中该元件
   ├─ 点到某条导线的距离 < 容差（点到线段距离）？    → 选中该导线
   └─ 都没命中                                     → 空白处
3. 再看"当前工具"决定做什么
```

整个优先级写在 `OnLeftDown()` 里，顺序是：
**导线工具 → 元件 → 导线 → 放置待放元件 → 框选**

### 工具状态机

`选择 / 导线 / 文本` 三种模式。**同一份鼠标事件，在不同模式下含义完全不同**：

| 事件 | 选择模式 | 导线模式 |
|------|----------|----------|
| 左键按下 | 选中 / 开始拖动 / 开始框选；有待放置元件时=放下它 | 放一个折点 |
| 右键按下 | 放弃待放置的元件 | 结束画线 |
| 鼠标移动 | 悬停高亮网络；有待放置元件时跟一个虚线幽灵 | 显示折线预览 |
| Esc | 不响应 | 结束画线 |

这就是"模式"的本质：**状态决定了事件的含义**。

关于"待放置"还有一个刻意的设计：**放下一个元件后自动退出待放置状态**。
早先的做法是放下之后仍然保持待放置（可以连着放多个），要靠 Esc 取消；
实际用起来经常"手一抖又放了一个"，而且 Esc 还兼着"取消选择"，
一次误按就把选中的东西全丢了。
现在改成：**放一个 → 立刻回到选择状态**（幽灵消失、元件库高亮也清空），
想连着放就再点一次元件库；想放弃就按右键。
于是 Esc 只剩下"结束画线"一个职责，把"取消选择"这条彻底删掉了。

## 2.7 导线与吸附的原理

### 正交折线

原理图惯例：**只允许水平/垂直线段**（便于观图和后续自动布线）。
所以一次单击可能生成 1~2 条线段（先横后竖的 L 形）：

```
起点 ●────────┐        先画水平段
              │        再画垂直段
              └────● 终点
```

### 吸附优先级：引脚 > 导线端点 > 网格

为什么是这个顺序？
1. **吸到引脚**最优先 —— 因为电气连接是靠"坐标完全相同"判定的，吸不准就接不上
2. **吸到导线端点**次之 —— 保证两根线能接上（端点重合即连通）
3. 都吸不到才**回到网格** —— 保证线看起来整齐

### 为什么引脚必须落在网格上（一个真实的坑）

引脚沿元件边的位置是 `y = 元件左上角y + 高 × (k+1) / (n+1)`，
整数除法后可能是 13、26 这种**不是 10 的倍数**的值。

于是：
- 点引脚 → 得到非网格坐标（y=13）
- 点空白 → 网格吸附得 y=10

两者打架，结果**点一下引脚、再点一下空白，就多出一段 3 单位的折角**。
现象是"导线数比预期多、网络被错误合并"。

**修复**：让引脚沿边的偏移量也对齐到 10 的倍数（`AlignPinOffset`），
元件左上角也对齐网格 → 引脚天然落在网格上。
（完整排查记录见 `README.md` 第 8.5 节，这是很好的答辩素材）

## 2.8 连通性算法原理（整个项目的技术核心）★

### 问题

给你一堆引脚和一堆导线，怎么知道**哪些引脚在电气上是连通的**？

### 关键洞察

> **把"连接点"当成图的节点，把导线当成边；坐标相同的点就是同一个节点。**

### 五条连通规则（与 KiCad / Logisim 一致）

| 情形 | 连通? | 原因 |
|------|-------|------|
| 两条导线端点重合 | ✅ | 坐标相同 → 同一个节点 |
| 导线端点落在另一条导线**内部** | ✅ | T 型连接，要画实心连接点 |
| 引脚落在导线上 | ✅ | 同上 |
| 两条导线**十字交叉** | ❌ | **交叉处没有任何"点"参与合并** |
| 两个引脚坐标重合 | ✅ | 同一节点 |

前三条的实现只有一句话：

```
① 每条导线把自己的两端合并（Unite）
② 所有"落在某条导线内部的点"，与该导线合并
```

**"十字交叉不连通"是这个设计最漂亮的地方** —— 不是靠写特例判断，
而是因为交叉处**根本没有节点存在**，所以天然不会连通。
（想让它们连通？在交叉处放一个连接点，那个点就会被合并进去 —— 语义自然成立。）

### 并查集（Union-Find）

用来维护"谁和谁是一伙的"：

```
Find(x)    找到 x 所在集合的代表元素
Unite(a,b) 把两个集合合并
路径压缩   把查找路径打平，让后续 Find 接近 O(1)
```

最后：**`Find()` 结果相同的点，属于同一个电气网络**。

### 从连通分量到"网络"

- 一个连通分量里**如果包含引脚** → 它就是一个"网络"，自动命名 N1、N2、…
  （如果连着 GND / VCC 元件，就用那个名字）
- 某个点上"接触"的导线数 ≥ 3（**穿过算 2 股**）→ 画一个实心连接点（junction）
- 只连了 1 个引脚的网络 / 悬空的导线端点 → ERC 会报警

**这就是从"画出来的图形"得到"电气语义"的全过程** —— 也是任务 6 仿真内核的输入。

### 为什么用并查集而不是别的

| 方案 | 复杂度 | 评价 |
|------|--------|------|
| BFS/DFS 遍历 | O(N+E) 每次 | 可行，但要显式建图 + 遍历 |
| **并查集** | 近似 O(N α(N)) ≈ O(N) | **代码最短（20 行）、天然支持"增量加线"** |

## 2.9 网表生成原理

有了网络，生成网表就变成**查表输出**：

```
网络 → 它包含哪些引脚          → 输出"网络清单"段
元件 → 每个引脚属于哪个网络     → 输出"元件清单"段
元件 → 按引脚顺序列出网络名     → 输出"SPICE 风格元件行"段
```

样例（`docs/sample-netlist.net`）：
```
* [N3] U1-Y U2-A U3-A          ← 三个引脚属于同一网络，因为 T 型连接把它们并起来了
* U1  与门   @ (-280, -20)
*     A -> N1
*     Y -> N3
XU1 N1 N2 N3 与门               ← SPICE 行：元件名 + 各引脚的网络名 + 模型名
```

**格式可替换**：所有格式逻辑集中在 `NetBuilder::ToNetlist()` 一个函数里，
要换成 Protel / KiCad 格式只需重写这一个函数，模型层和界面层都不用动。

## 2.10 文件序列化原理

**序列化** = 把内存里的对象树变成一维的字节流（写文件），以及反过来（读文件）。

```
内存                          磁盘
vector<ComponentInstance>  →   <component name="与门" refdes="U1" x="-280" .../>
vector<Wire>               →   <wire x1="-210" y1="0" x2="210" y2="0"/>
```

**为什么选 XML 而不是 JSON / 二进制 / 自定义文本**：
1. wxWidgets **内置** `wxXmlDocument`（`wxUSE_XML=1`，编译时已自动链接），不引入任何第三方库
2. 自描述、可读、可手改 —— 调试和答辩演示都方便
3. 有正式的转义/编码规则，中文和特殊字符不会踩坑
4. 二进制体积略小但要自己写序列化，不便于调试

**一个重要的设计决策**：把**引脚定义**也写进文件，而不是只存元件名。
这样文件是**自包含**的 —— 将来元件库升级、甚至支持用户自定义元件后，旧文件依然能正确还原。

## 2.11 撤销/重做原理（快照式）

```
每次会改变文档的操作【之前】：
    把整份文档（元件表 + 导线表 + 编号计数器 + 位号计数）复制一份，压入撤销栈

Undo：把当前状态压入重做栈，弹出撤销栈顶，整体替换回文档
Redo：反过来
```

同一个操作只压一次快照（比如一次导线单击可能生成 2 条线段，但只算一步撤销）；
拖动移动只在"真正开始移动"时压快照，单纯点击选中不产生撤销步。

选择快照式而不是 Command 模式的理由，见 `README.md` 第 5A 节（一张完整的三方案对比表）。

## 2.12 仿真原理（任务 6）

### 先说清楚：仿真在算什么

原理图上有两种东西：**图形**（线、方块、文字）和**电气语义**（谁和谁连着）。
2.8 节的并查集已经把前者变成了后者 —— 得到一张"网络 → 引脚"的表。
仿真要做的只有一件事：**给每条网络算出一个逻辑值**（0 / 1 / 未知）。

```
元件（逻辑功能）  +  网络上的值  ──反复套用──→  每条网络的值稳定下来
```

### 为什么不能"一遍算完"，非得反复迭代

因为电路里有**反馈**。比如把一个非门输出接回它自己的输入，或者更常见的：
A 门的输出影响 B 门，B 门的输出又影响 C 门，C 门绕回来影响 A 门。
一条导线上的值可能"因为下游还没算完"而暂时是错的。

所以采用**固定点迭代**（fixed-point iteration）：

```
1. 所有网络的值先置成"未知 X"
2. 把每个元件的输入值读进来，按它的逻辑功能算出输出，写回输出网络
3. 如果这一轮里没有任何网络的值变了 → 收敛，停
4. 否则重复，最多 max(30, 元件数×6+20) 轮
```

**"值不再变化"就叫收敛**（收敛到一个不动的点 = fixed point）。
轮数上限是保险：真的收敛不了（比如振荡环），就停在那里并把没定下来的网络报成 X，
绝不无限循环把界面卡死。报告里那句"迭代次数 : 2"就是这个循环实际跑了几轮。

### 为什么是"三值"逻辑而不是 0 / 1

只用 0 和 1 的话，遇到下面三种情况就没法回答了：

| 情况 | 举例 | 只能答"不知道" |
|------|------|----------------|
| 没有驱动 | 一条线只有一端接了门，另一端空着 | 它到底是 0 还是 1？ |
| 多个驱动打架 | 两个输出同时接到同一条线，一个给 0 一个给 1 | 听谁的？ |
| 环路没收敛 | 上面说的反馈环 | 稳定值是多少？ |

所以引入第三个值 **X（未知）**，并且规定"X 会污染"：与门只要有一个输入是 0，
输出就是 0（0 与任何值都是 0，这条规矩叫**短路求值**）；否则只要有一个 X，输出就是 X。
这就是数字电路里 0/1/X 三值仿真的标准做法，也是电路仿真软件（ModelSim 之类）的基本套路。

### 元件怎么知道自己该干什么

不新建一套模型，而是**按元件名查表**（`SimKindOf()`）：名叫"与门"就做与运算，
名叫"半加器"就展开成 S = A⊕B、C = A·B。这个映射表是 `SimModel.cpp` 里一个
`switch`，加一种新元件只需要加一个 `case`。

输入引脚、常量当作**激励源**（它的值由用户点击决定）；
输出引脚、探针、网络标签当作**观察点**（不驱动任何东西，只显示所在网络的值）。

### "实时"是怎么做到的

关键在**改值之后立刻重算**：点一下输入引脚 →
`OnLeftDown` 里先调 `ToggleInputAt()` 把源的值取反 → 再调 `RecomputeSimulation()` 重跑迭代 →
最后 `Refresh()` 触发重绘。整个链路是同步的，所以松开鼠标那一刻画面就已经是新结果了。

而重绘时导线用哪支笔，取决于它所属网络的逻辑值：

```cpp
if (仿真中) 颜色 = NetColourFor(该网络的值);   // 高=绿，低=灰蓝，未知=琥珀
else        颜色 = 普通绿色;
```

这里有个刻意的优先级：**仿真着色盖过"网络高亮"色**。
否则鼠标一悬停，整条线变成橙色，仿真结果就被盖掉了 —— 演示时容易看成"没生效"。

### 时钟源为什么是"手动单步"

真正的时序仿真需要一个时间轴和事件队列（到第几纳秒、哪个门翻转发什么事件）。
本次实现的是**组合逻辑 + 手动时钟**：按一下 `Space`，时钟相位取反，然后整套电路重新求一次值。
它足够演示"输入变化 → 输出跟着变"的因果，但画不出波形图 —— 这也是任务 6 剩下的部分。

## 2.13 元件库：内置清单 + 用户 XML 怎么合成一份

元件库看着是个树，背后其实是个"两份数据合成一份"的小问题。

### 两份数据

| 来源 | 存在哪 | 谁改它 |
|------|--------|--------|
| **内置元件** | 写死在 `ComponentCatalog.cpp` 的 `BuiltinData()` 里 | 程序员 |
| **用户自定义元件** | 程序目录下的 `components.xml` | 用户（手改文件，或用"元件库管理"对话框） |

为什么内置的要写死在代码里？因为**拷走一个 exe 就能用**，不依赖任何数据文件。
为什么用户那部分要放外面？因为用户不该为了加一个元件去重新编译程序。

### 合成规则（合并算法）

```
1. 先把 26 个内置元件复制成"合并表"
2. 逐个读用户的元件：
     名字在合并表里已经有 → 用用户的字段覆盖那一条（= 定制内置元件的默认值）
     名字是新的          → 加进"用户自定义"这个分类（没有就新建一个）
3. 合并表就是界面看到的最终结果
```

这条规则产生两个很实用的效果：

- **扩展**：加一个"三输入与门"，元件库里就多一个，引脚按 `输入=3` 自动生成 A/B/C+Y；
- **覆盖**：写一个名字叫"电阻"、元件值填 `1k` 的条目，元件库里那个电阻的默认值就变了，
  但分类位置还是原来的"无源器件"，不重复、不新增。

### 什么时候必须重建界面

合并表的元素是**按值存在 vector 里**的，树节点上挂的是指向它们的指针。
一旦重新加载（`Reload()`），vector 重新分配，**所有旧指针立刻失效**。

所以每次重载后必须做三件事，少一件就是野指针：

1. 清掉"待放置元件"（`SetPendingComponent(nullptr)`）；
2. 清空选择、重新建树（`LibraryPanel::Reload()`）；
3. 清掉图标缓存（图标是按"形态 + 是否自定义"缓存的）。

### 搜索框是怎么"过滤"的

不是把树节点删掉，而是**重新建一棵只含命中项的树**：

```
关键词 → 转小写 → 对每个元件的 "名称 + 说明 + 元件值 + 封装" 拼串后搜子串
       → 分类名命中就把整类都放进去
       → 一个都没命中时，插一行"没有匹配「xxx」的元件"
```

这样做的好处是不用维护"某一行原来在哪"的状态，换个关键词整套重建即可；
代价是每次输入都重建树，但 30 个节点量级完全无感。

### 符号缩略图为什么是"画"出来的

树里 16×16 的图标和底部的大号预览都是运行时用 `wxDC` 画的，没有任何图片文件：

- **树图标**：18×18、纯黑硬边线条、**关掉抗锯齿**——这是故意学 Logisim 的观感
  （它用 Java 画小图本来就不做抗锯齿，边缘是硬的）；自定义元件用橙色描边区分来源；
- **底部预览**：按元件真实宽高比画方框 + 真实引脚位置 + IEEE 记号（`&` / `≥1` / `=1` / `1`）
  + 取反小圈 + 封装与说明文字。

好处和高 DPI 关系很大：没有位图，就不存在"放大就糊"。

> 一个踩过的坑：预览面板用了 `wxAutoBufferedPaintDC`，但忘了在构造函数里
> `SetBackgroundStyle(wxBG_STYLE_PAINT)`。Release 版毫无反应，**Debug 版一画就弹断言**。
> 这类"只在 Debug 才炸"的问题，靠 `SE_ASSERT_LOG=1` 把断言写进 `assert.log` 才定位得到。

### 元件图形：为什么单独抽一个绘制器

一开始元件的画法散在三处：画布画矩形 + 引脚名，元件库预览自己再画一遍，
树图标又用第三种画法。结果就是**预览里看到的和放到画布上的不一样**——
用户第一反应是"这俩是不是两种元件"。

现在改成：**形状只定义一次，三处都调它**（`SymbolPainter`）。

```
                 ┌──────────────────────────┐
 画布(放好的元件) → │                          │
 画布(待放的幽灵) → │   SymbolPainter::        │ → 17 种形状：
 元件库大号预览   → │   PaintSymbolBody/Pins/  │   与门 D 形、或门盾形、异或门多一条弧、
 元件库 16×16 图标 → │   Labels                 │   非门三角+小圈、加法器方框带 +、
                 └──────────────────────────┘   端口五边形、电阻锯齿、电容极板、
                                                电感线圈、二极管/LED、三极管、
                                                运放三角、电源/地、探针、标签
```

几个关键决定：

1. **坐标按"外框局部坐标"写**：`(0,0)` 是元件外框左上角，`(comp.w, comp.h)` 是右下角，
   再用一个 `SymbolPlacement`（屏幕原点 + 缩放）映射过去。这样同一份代码
   既能在画布上按 100% 画，也能在 16×16 的树图标里按 0.2 倍画。
2. **引脚位置不自己算**：直接调 `PinAnchor` / `PinPosition`。
   否则形状和导线接点迟早对不上——那种 bug 特别难查（线看着连着，网表却断着）。
3. **`ComponentInstance` 里没有"元件类型"字段**（`.ses` 也只存引脚），
   所以绘制器从引脚摆放反推形态：底部有脚 = 电源，只有 1 个脚 = 端口，左右各一脚 = 两端器件。
4. **元件旁边只写位号**（`U1` / `R2` / `OUT1`），不写"与门""电阻"这类类型名。
   形状已经说明是什么了，再压一行字只会挡住图形——这一点和 Logisim 的做法一致。
5. **树图标是单色线条**（深灰描边、白底、只画本体），和 Logisim 的元件库图标一个风格；
   16×16 下再画引脚就糊成一团，所以图标省掉引脚，靠轮廓辨认。

画「异或门」时还踩过一个坑：额外那条弧如果弧度和本体左边缘一样大，
中段会被本体的填充盖住，只剩上下两截，看着像个尖角。
把弧度调到明显更小（`bw * 0.16`）之后才是正常的"平行双弧"。

## 2.14 画导线时那三个"手感"问题

这三个问题都是同一个根源：**画布只知道自己画了什么，不知道用户在犹豫什么**。

### 问题一：靠近引脚时没有"要接上了"的反馈

光标离引脚还有十几个像素，用户不知道这一下会接到引脚、还是落在网格空白处。
点下去才发现差一点——只能撤销重画。

做法是给吸附函数加两个出口：除了吸附到的坐标，还告诉调用方"吸到了什么"
（引脚还是导线端点）和"它的名字"（`引脚 U2-A`）。拿到信息后，在接点上画三样东西：

1. 一圈**虚线光环**（半径 11px，随缩放略变），像瞄准镜；
2. 四段**十字准星**，绕开中心，不压住接点本身；
3. 中心一个 7px **实心点**——这一点最要紧，它表示"已经咬住了"。

再加一块名字牌（白底 + 彩色描边），摆在光环右上方、不挡元件。
颜色当作语义用：**绿＝引脚、橙＝导线端点**，用户不用读字也知道接的是什么。

标记画在 `DrawWirePreview()` 的最后一步，保证它压在所有图元上面——
否则会被元件本体的填充盖掉一半。

### 问题二：画完一段还得手动退出

原来一段线画完（落点接上了东西）工具仍停在"导线"，想挪个元件得先按右键或 Esc。
现在改成：**落点正好在接点上，就自动收尾并切回选择工具**。

判断"落点是不是接上"只有一行：

```cpp
const bool landed = FindNearbyAttachPoint(p, attachPoint, &attachKind) && attachPoint == p;
```

`attachPoint == p` 这个条件把"吸到了别处"排除掉——只有吸附点和点击点完全重合，
才算真的落在接点上。落在空白处则继续画下一段（连续画线没被破坏）。

画布不直接去改工具栏和状态栏，而是回调宿主 `OnWireFinished`，由 `MainFrame` 统一
切工具、同步按钮状态、写提示。这条"画布只管几何、界面只管界面"的分界一直保持。

### 问题三：拖动元件时导线变成斜线

这是最麻烦的一个。原来的实现是：拖动元件时，把贴在它引脚上的导线端点
按位移整体平移（`端点 = 原始端点 + delta`）。引脚挪到哪儿它就跟到哪儿，
但**角度不管**——横线会变成斜线，看着像断了一样。

正确做法是让**拐角**去承担变形。设被拖的引脚在新位置 `newPin`，
另一端（不动的那端）是 `fixedOther`：

- 如果原来这条线是**竖的**（`a.x == b.x`），拐角就取 `(fixedOther.x, newPin.y)`；
- 如果原来这条线是**横的**，拐角就取 `(newPin.x, fixedOther.y)`。

这样"跟着引脚的那条线"永远保持原来的走向，另一条永远保持与它垂直，两个角度都是 90°。
实现上把**两条**线段的端点都改写成这个拐角：被拖的线写 `newPin`，
它自己的另一端和伙伴线的拐角端都写 `corner`。

还有一个边界情况：如果那个引脚只连了一条线（没有伙伴线），
光改它自己就没有"另一条"可垂直——这时**现场补一条零长度占位线段**顶上去，
让拐角有地方落；松手时再把 `a == b` 的线段过滤掉。
（不能用 `AddWire()` 加，因为它会拒绝零长度线段，所以直接 `m_wires.push_back`。）

顺手还处理了一个细节：如果一条线的**两端都接在被拖元件上**，那它整体平移角度不变，
跳过就行，不需要重新摆拐角。

!> 踩过的坑：补出来的临时线段会改变 `m_wires` 的下标，
所以 `EndDrag()` 里必须先过滤、再 `m_selWires.clear()`，否则选中状态会指向错误的线段。

## 2.15 全流程串一遍：从一次鼠标点击到一张网表

以"用导线把 U1 的输出连到 U2 的输入"为例：

```
① 用户点工具栏"导线"按钮
   → OnCommand(ID_TOOL_WIRE) → canvas->SetTool(ToolWire)

② 用户在某处单击
   → WM_LBUTTONDOWN → wx 翻译成 wxEVT_LEFT_DOWN → OnLeftDown()
   → 屏幕坐标 → 世界坐标（ToWorld）
   → 工具是 ToolWire → HandleWireClick()
   → SnapForWiring()：先找附近引脚/导线端点，找不到才吸网格
   → m_wireDrawing = true，记下起点
   → Refresh() → 系统发 WM_PAINT → OnPaint() 画出虚线预览

③ 用户再单击一次
   → HandleWireClick()：PushUndo() 压快照
   → 正交折线：先生成水平段（AddWire），再生成垂直段（AddWire）
   → m_netsDirty = true（标记连通性缓存失效）

④ 用户在空白处右键
   → FinishWire() → GetNetGraph()
   → NetBuilder::Build()：登记所有引脚和导线端点为"节点"
                          → 并查集合并导线两端
                          → 把所有落在导线内部的点与该导线合并
                          → 归并出网络，判定连接点
   → 状态栏显示"当前共 N 条线段，M 个网络"

⑤ 用户点菜单「检查 → 查看网络表」
   → OnCommand(ID_INSPECT_NETLIST)
   → canvas->BuildNetlist() → NetBuilder::ToNetlist()
   → 弹出对话框显示文本，可保存成 .net 文件

⑥ 悬停在导线上
   → OnMouseMove → UpdateHoverNet() → 查出该导线属于哪个网络
   → DrawWires()/DrawComponents() 用橙色重画整个网络
   → DrawWirePreview() 在光标旁画出 "N3 (3 引脚)" 气泡
```

**这六步覆盖了本项目绘图与数据链路的核心机制**：事件分发、坐标变换、吸附、正交折线、
连通性求解、网表生成、悬停高亮。答辩时照这条线讲一遍，逻辑最完整。

如果还想往上加一段，就接上仿真：**⑦ 点工具栏「仿真」→ 每条网络拿到一个 0/1/X → 导线按值变色**，
再多一句"改输入引脚的值会立刻重算"，任务 6 就讲完了（原理见 2.12）。

# 第三部分 · wxWidgets 到底起什么作用

## 4.1 一句话定义

> **wxWidgets 是一个跨平台的 C++ GUI 框架。它把"操作系统底层的窗口、控件、绘图、输入"包成一套统一的 C++ 类，
> 让同一份代码在 Windows / macOS / Linux 上都能编译运行。**

在本工程里，它是**地基和脚手架**：
窗口、控件、事件、绘图、字符串、XML 这些"每做一个桌面程序都要重写一遍"的东西由它提供；
而"电路原理图编辑器"独有的东西（引脚级网络模型、连通性算法、网表格式、绘图区交互）全部是我们自己写的。

用量：**157 个不同的 wx 符号，出现 938 次**。

## 4.2 没有它的话，要写多少东西

在 Windows 上创建一个带菜单的窗口，用裸 Win32 API 大致要写：

```c
WNDCLASSEX wc = { ... };
RegisterClassEx(&wc);                    // 注册窗口类
HWND hwnd = CreateWindowEx(...);         // 创建窗口
HMENU hMenu = CreateMenu();              // 菜单要手工建
AppendMenu(hMenu, MF_STRING, ID_NEW, L"新建");
...
InitCommonControlsEx(...);               // 工具栏要额外初始化
while (GetMessage(&msg, ...)) {          // 自己写消息循环
    TranslateMessage(&msg);
    DispatchMessage(&msg);
}
LRESULT CALLBACK WndProc(HWND, UINT msg, WPARAM, LPARAM) {
    switch (msg) {                       // 几十个 WM_XXX 要自己分派
    case WM_PAINT: { PAINTSTRUCT ps; HDC hdc = BeginPaint(...);
                     HPEN pen = CreatePen(...); SelectObject(hdc, pen);
                     MoveToEx(...); LineTo(...);
                     DeleteObject(pen);   // GDI 资源必须手工释放
                     EndPaint(...); } break;
    case WM_LBUTTONDOWN: ...
    }
}
```

wxWidgets 把它变成：

```cpp
class MainFrame : public wxFrame {
    MainFrame() : wxFrame(nullptr, wxID_ANY, L"Schematic Editor") {
        wxMenu* fileMenu = new wxMenu;
        fileMenu->Append(wxID_NEW, L"新建\tCtrl+N");
        Bind(wxEVT_PAINT, &MainFrame::OnPaint, this);
    }
};
```
GDI 句柄、资源释放、消息循环、消息分派全都不需要写。

## 4.3 它在本工程里干的五件事

### (1) 窗口与控件 —— 封装操作系统原生控件

| wx 类 | 我们用它做什么 | 底层其实是（实测枚举到的窗口类） |
|-------|----------------|-------------------------------|
| `wxFrame` | 主窗口 | 原生窗口（类名 `wxWindowNR`） |
| `wxPanel` | 三个面板 | 子窗口 |
| `wxTreeCtrl` | 元件库树 | **`SysTreeView32`** |
| `wxToolBar` | 17 个按钮 | **`ToolbarWindow32`** |
| `wxStatusBar` | 5 段状态栏 | **`msctls_statusbar32`** |
| `wxMenuBar` / `wxMenu` | 8 个菜单 76 项 | `HMENU` |
| `wxPropertyGrid` | 属性表 | wx 自绘控件 |
| `wxSplitterWindow` | 可拖拽分栏 | wx 自绘控件 |
| `wxTextCtrl` | 网表/ERC 报告框 | **`RichEdit50W`** |

> **重要结论**：上表第三列是我们在验证时用 `GetClassNameW` 枚举出来的**真实 Windows 窗口类名**。
> 这说明 wxWidgets **不是自绘一整套界面，而是封装操作系统原生控件** ——
> 所以程序看起来就是标准 Windows 程序的样子，而且**自动跟随系统主题、高对比度、输入法**。

### (2) 事件系统 —— 把消息循环包成回调（GUI 框架最核心的作用）

```
底层：操作系统把 WM_LBUTTONDOWN 投递到窗口过程，你在巨大的 switch 里分派
wx：  翻译成 wxEVT_LEFT_DOWN，通过 Bind 派发到你自己写的成员函数
```

我们代码里这一行：
```cpp
Bind(wxEVT_LEFT_DOWN, &SchematicCanvas::OnLeftDown, this);
```
替代了 `WndProc` 里几十个 `case`。而且 `wxEVT_LEFT_DOWN` 在 macOS 上来自完全不同的底层事件，
**同一份代码不用改** —— 这就是"跨平台"在事件层面的体现。

本工程用到的 8 个事件类：`wxMouseEvent` / `wxKeyEvent` / `wxCommandEvent` / `wxTreeEvent` /
`wxPaintEvent` / `wxSizeEvent` / `wxCloseEvent` / `wxEraseEvent`。

### (3) 绘图与几何 —— 统一 GDI / GDI+ / Direct2D，并提供抗锯齿

- `wxGraphicsContext`（新式：浮点坐标 + 抗锯齿，Windows 上底层是 GDI+ 或 Direct2D）
- `wxDC`（老式：整数坐标）
- `wxAutoBufferedPaintDC` —— **双缓冲一行搞定**，彻底解决闪烁
- 几何/样式值类型：`wxPoint`（用了 116 次）/ `wxPoint2DDouble`（62 次）/ `wxSize` / `wxRect` /
  `wxColour`（37 次）/ `wxPen` / `wxBrush` / `wxFont` / `wxCursor`

> 有意思的是：**这些"小工具类"占了 wx 使用量的一大半**。
> 它们的作用其实是给 C++ 补上一个好用的**几何/样式值类型库**（标准库没有这些）。

### (4) 工具类 —— 不是 GUI 的，但也由 wx 提供（省掉第三方依赖）

| 类 | 用在哪 | 替代了什么 |
|----|--------|-----------|
| `wxString`（**用得最多，191 次**） | 全工程 | 支持 Unicode、格式化、各种编码转换的字符串 |
| `wxXmlDocument` / `wxXmlNode` | `.ses` 文件读写 | **省掉一个 XML 第三方库** |
| `wxFile` / `wxFileName` | 保存/加载/路径处理 | 文件与路径操作 |
| `wxFileDialog` | 打开/保存/导出对话框 | 系统文件对话框 |
| `wxArtProvider` | 元件库树的标准图标 | 取系统图标 |
| `wxBitmapBundle::FromSVG` | **17 个工具栏矢量图标** | wx 3.2 内置 nanosvg，**省掉图标资源文件和第三方 SVG 库** |
| `wxDateTime` | 网表里的生成时间 | 日期时间 |
| `wxConvUTF8` | 文本按 UTF-8 写出 | 编码转换 |

### (5) 消息框等便捷设施

`wxMessageBox`（未保存提示、导出成功提示）、`wxAboutBox`（关于对话框）。

## 4.4 它的工作原理

```
        我们的代码（跨平台，只写一次）
                 ↓
        wxWidgets 统一 C++ API
                 ↓  编译时选择"端口"(port)
    ┌────────────┼────────────┐
  wxMSW        wxGTK        wxOSX
    ↓            ↓            ↓
  Win32        GTK+         Cocoa
```

在 Windows 上用的是 **wxMSW 端口**。证据：工程链接的是 `wxmsw32u_core.lib`，
**`msw` 就是 "Microsoft Windows" 的缩写**，`u` 表示 Unicode 构建。

技术上是**薄封装 + 事件抽象 + 少量自绘控件**：
- 能用原生控件的就用原生（树、工具栏、状态栏、编辑框）→ 外观和行为都原生
- 原生没有的才自绘（属性表、分割条）→ 保证跨平台一致

## 4.5 它的边界：它不做什么（这一点最重要）

| 它**不**做 | 谁来做 |
|------------|--------|
| 什么是"连通"、谁和谁是一个网络 | 我们写的 `NetModel`（并查集） |
| 网表长什么样、怎么导出 | 我们写的 `NetBuilder::ToNetlist()` |
| 图数据结构、拓扑排序、撤销栈 | 我们自己写的算法 |
| 元件画成什么形状、导线怎么折 | 我们在 `OnPaint()` 里自己画 |
| 工程设计规则（ERC） | 我们写的 `RunErc()` |

> **它只提供"能显示、能交互"的能力，不提供"显示什么、算什么"的知识。**
>
> 这个边界正是我们三层架构的由来：
> **UI 层用 wxWidgets，模型层和算法层完全自己写，两者互不知道。**

## 4.6 为什么选它（可行性研究可用的理由）

| 理由 | 说明 |
|------|------|
| **任务书指定** | 任务描述 PPT 第 4 页明确要求"界面实现方法：基于 wxWidgets 的图形化编程" |
| 跨平台 | 一套代码可编译到 Windows / macOS / Linux |
| 原生外观 | 封装系统原生控件，不是自绘皮肤 |
| **零第三方依赖** | 自带 XML、PNG/JPEG/TIFF、属性表、树控件、SVG 解析 —— 整个工程除 wx 外无任何外部库 |
| C++ 原生 | 与 VS2022 / MSBuild 配合良好，静态链接后 exe 可独立分发 |
| 文档与样例齐全 | 自带 200+ 官方 sample，桌面文件夹里也有 `wxWidgets进行跨平台程序开发.pdf` |

**对比过的替代方案**（报告"多方案对比"用）：Qt（LGPL/商业授权、体积大）、
Electron/Web 前端（非原生、体积巨大）、Python + PyQt（性能与分发劣势）、
MFC（仅 Windows、老旧）。选 wxWidgets 的主要理由是**任务指定 + 零依赖 + 原生外观**。

# 第四部分 · 答辩时可以这样一句话概括原理

> 这个编辑器的数据是一张图：元件是带引脚的节点，导线是连接它们的边。
> 我用**世界坐标**存储所有几何信息，绘制时通过"原点 + 缩放"的仿射变换映射到屏幕，
> 所以缩放平移完全不改数据。用户操作被翻译成对图的修改，
> 然后用**并查集**求解连通分量，把"图形"变成"电气网络"，进而导出**标准网表**。
> 界面、模型、文件三层的接口是分离的，所以换渲染方式或换网表格式都不影响其他部分。
